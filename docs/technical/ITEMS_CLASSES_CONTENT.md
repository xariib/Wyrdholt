# Items, class tree and content schema

## Item instances

Catalog definitions and owned copies are separate types.

| `ItemDef` (content) | `ItemInstance` (player data) |
|---|---|
| `id`, `name`, `slot`, `rarity`, `stats`, `effect`, `minEncounterLevel`, `tags`, `icon` | `id` (stable, unique), `baseId`, `acquiredSeq`, `isNew` |
| | Reserved, unused in the spike: `rolls`, `modifiers`, `provenance`, `upgrade`, `seasonal` |

**Rules**

- **Id assignment:** ids come from `profile.inventory.nextInstanceId`, a per-character monotonic counter, and are assigned in `createInstance()`. They are never random, so a replay reproduces them (B5).
- **Id-only references:** equipment, queued changes (`profile.pending`), NEW/reviewed state and reservations (`reservedInstanceIds()`, for a future Forge) all reference instance ids.
- **Stable storage:** instances stay sorted by id, with O(log n) lookup (`findInstance`). Ids survive save/load (tested).
- **Compact saves:** plain instances are grouped per catalog item. Instances with per-instance data are stored in full. Adding rolled stats later requires no ownership rewrite.
- **UI grouping:** the UI groups identical catalog items into one row with a copy count, matching LOOT_FORGE behaviour. Equipping a group picks a copy that is not already equipped. Opening a comparison marks that group's copies reviewed.
- **No random affixes or Ancient items** are implemented.
- **Provenance** (`stage` / `cache` / `starter` / `dev-grant`) is recorded in memory. Schema 1 does not persist it.

**Rarities** are data (`RarityDef`: `order`, `color`, `notable`), so a future Ancient tier is a content change.

**Loot** (`loot/loot.ts`):

- Draw order: drop chance → rarity by weight → uniform pick among eligible items.
- Eligibility uses the **encounter level**.
- The table's `maxRarity` is enforced in code.
- A rarity with no eligible items falls back downward.
- `rollLoot(..., chanceScaleBp)` multiplies the table's drop chance. Stage drops pass `lootChanceScaleBp(config.lootFullChanceMs, fight duration)`: 100% for victories of at least 10 s, proportionally less below. Caches pass 100%.
- **Tables per zone (C1):** `<zone>_farm` (1.5%), `<zone>_boss` (4%) and `<zone>_cache` (100%). Rarity weights follow PROGRESSION_BALANCE. The max rarity is Rare (Greenfields), Epic (Darkwood) and Legendary (Ashen). Values are in [GAME_DESIGN.md](../GAME_DESIGN.md#zones).
- **Completion cache:** `zone.cacheLootTableId` (falls back to the boss table). The first clear always rolls; repeat clears roll with `cache.repeatRollChanceBp` on their own seed stream (`cache/gate`).

**Catalog:** the original C1 catalog had five rarities × six slots = 30 items.
The current catalog has 344 live class-specific items, including 216 Rare–Legendary
stat specializations across all four classes and six slots, plus archived shared
definitions retained for compatibility. [Build options](../design/GEAR_BUILD_OPTIONS.md).

- Common, Uncommon and Rare come from PROGRESSION_BALANCE.
- ITEM-EFFECTS-006 supplies the remaining four Epic and six Legendary effects.
  All twelve high-rarity items now have named effects; stats, existing effects and
  acquisition gates stay unchanged. Parameters and ward/status rules:
  [C3_ITEM_EFFECTS](../design/C3_ITEM_EFFECTS.md). Values are provisional playtest
  tuning, content `emberbound-content/0.5.0-c3-items-test`.
- Encounter level gates: Rare 5, Epic 9, Legendary 13.

## Class tree

`ClassDef` fields:

- `id`
- `parentClassId` (null for base classes)
- `tier` (1 = base)
- `unlockRequirements`, with these kinds:
  - `characterLevel`
  - `masteryRank`
  - `trialCleared`
- `masteryTrackId`
- `implemented`

The spike ships all four base classes as data:

- **Monk and Mage** are implemented (C1).
- **Warrior and Ranger** are implemented on branch `c2-warrior-ranger` and calibrated against Monk/Mage (22 Sep 2026, reports/C2_FOUR_CLASS.md; first provisional kits: reports/C2_PREP.md). On the C1 branches (`c1-playtest`, `c1-hotfix`, `c1-retune`) they are still `implemented: false` and shown only as "later build".
- **Promotions** would be tier-2 classes pointing at their base class, with requirements like `[characterLevel N, masteryRank base 20, trialCleared T]`. Their own `masteryTrackId` gives each promotion its own M1–M20 track.

Nothing assumes whether the Active and Alternate classes can both be promoted.

### Class Mastery

- **Track data:** `MasteryTrackDef` holds `maxRank` 20, `milestones` [1, 5, 10, 15, 20], the XP table, an attack foundation (C1 retune: +2.5% of the class's base attack per rank above M1, added in hundredths of attack, rules 0.3.0) and a list of techniques.
- **XP tables:** `ProgressionDef` is either `{ curve }` (Phase B geometric curve) or `{ steps }` (explicit XP per step, C1). `config.levelXp` and every `track.xp` use steps generated by `tools/sim/fit-tables.ts` (`packages/game-content/src/progression.ts`). A steps table must have exactly `max − 1` positive integer entries.
- **Techniques:** a technique **adds** mechanics or **patches** parameters of mechanics already unlocked, for example Practiced Rhythm sets `combo_strike.potencyBp = 9500`. `resolveClassMechanics(content, classId, rank)` builds the kit at fight start. The catalog is never mutated.
- **Mechanic vocabulary** (shared by class techniques and item effects):
  - `nth_hit_heal`
  - `nth_hit_extra_damage` (optional `requiresStatus`; C2: optional `requiresTargetHpBelowBp`)
  - `nth_hit_haste`
  - `on_hit_dot`
  - `nth_attack_splash`
  - `on_hit_echo`
  - `on_hit_chain`
  - C2: `on_damaged_retaliate`, `execute`, `nth_attack_split`, `armor_pierce`, `stack_burst` (behavior in C2_PREP §3)
  - C2: `ward` (`startBp`, `every`, `potencyBp`, `capBp`): a damage-absorbing pool. The hero starts every fight with `startBp` of max HP (it never carries over between fights); every `every`-th hero attack adds `potencyBp` of attack, up to `capBp` of max HP. Enemy hits and DoT ticks on the hero drain it after armor and minimum damage, then HP. No randomness. Several wards share one pool (starts add up, the highest cap wins). Hit/tick events on the hero carry `abs` and `ward` only when the kit has a ward, and `FightCounters.absorbed100` exists only then, so fights without a ward are byte-identical to before (C2_FOUR_CLASS §2)
- **Status ownership (C2):** every hero status line has one owner. Class mechanics resolve first, then items in slot order. A later mechanic that names a status already owned by another gets its own line, `status:mechanic` (a Warrior's class Bleed is `bleed`, Bloodletter's Rend on that Warrior is `bleed:rend`). Stacks, caps, damage and attribution are kept per line, and `stack_burst` only consumes its own kit's line. The renderer colours a line by its family (the part before `:`).
- **Kit validation (C2):** `validateKits` (`packages/game-core/src/content/kits.ts`) runs when a `ContentIndex` is built. It checks, for every implemented class at every rank from M1 to M20:
  - parameter ranges
  - unique mechanic ids, and no clash with item effect ids
  - techniques on milestones and in unlock order
  - patches only of unlocked mechanics
  - `requiresStatus` granted by the kit
  - a `stack_burst` that can reach its stack count
  - `appliesDots` only in a kit that has a DoT
  - a `ward` whose `startBp` is not above its `capBp`

Implemented kits on `c2-warrior-ranger` (content `emberbound-content/0.4.0-c2`). Monk/Mage techniques come from MASTERY_AUDIT and were tuned by the C1 class targets and the C1 retune; Warrior/Ranger numbers come from the C2 four-class calibration (reports/C2_FOUR_CLASS.md).

## Content schema (season- and date-ready)

- **`ContentSnapshot`:** `contentVersion`, `config`, rarities, classes, mastery tracks, items, enemies, zones, loot tables, rules and starter items. The snapshot is hashed (`ContentIndex.hash`) and every number must be an integer.
- **Zones** (`ZoneDef`):
  - ordered `stages` (count from data, not hard-coded)
  - `unlocks`, never auto-entered
  - loot tables (`lootTableId`, `bossLootTableId`, optional `cacheLootTableId`), first-clear gold, trail stage, `background` (renderer theme)
  - `stageRewards`: XP/gold base and per level, optional mastery overrides (`masteryBase10`, `masteryPerLevel10`), `eliteMultiplier`, `bossMultiplier`
  - `cache`: XP, gold, mastery, rolls, optional `repeatRollChanceBp`
  - optional `recoveryBp`, `ruleIds`, `availability`, `hidden`, `implemented`
- **Stages** (`StageDef`): `role` (normal / elite / boss), `level`, `hpBudget` and `dpsBudget100` for the **whole group**, 1–3 enemy archetype ids, and `ruleIds`. Members share the budgets by archetype weights (`encounter/budget.ts`).
- **Solo Bosses** (`SoloBossDef`) define an Adventure clear requirement, a single opponent, and an ordered list of tier budgets. C4 records the Ashen Crown in the build snapshot as `artifactId` and `artifactAttackBp` once earned.
- **Rules** (`RuleDef`): `kind` (`enemy_hp_bp` | `enemy_damage_bp` | `dot_damage_bp`), `valueBp`, optional `availability { startMs, endMs }`, and `testOnly`.
  - `resolveActiveRuleIds(content, zone, stage, atMs, extra)` resolves them when a fight starts.
  - The result is stored in the `FightRecord` as part of the content snapshot, so replays never need the clock.
  - The spike ships only test rules (`test_enemy_hp_150`, `test_enemy_soft`, `test_enemy_tough`, `test_windowed_embers`), exercised by the self-test and unit tests.
- **Future season content** plugs into these same fields:
  - A **Season Boss ladder** is a zone-like definition with a finite stage list and an `availability` window.
  - A **Season Rule** is a `RuleDef` with a window.
  - A **Season Relic** will have seasonal instance state. Its placement alongside permanent Artifacts remains open.
- **Content versioning:** `contentVersion` is recorded in every save and record. Solo Boss records use `ContentIndex.bossHash` to pin the ladder and shared combat content. The Adventure hash excludes the ladder. Regenerate affected golden hashes deliberately after a content change.
